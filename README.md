## 1. 快速开始

```powershell
# 前置：安装 MinerU（见第 7 章）
pip install mineru

# 转换单个 PDF，输出到同目录同名 .md
python pdf2md_mineru.py 论文.pdf

# 递归处理目录下所有 PDF
python pdf2md_mineru.py ./papers/
```

运行输出：

```
pdf2md_mineru 1.0.0 | MinerU: C:\...\Python313\Scripts\mineru-kit.EXE | 档位: basic | 待处理 1 个 PDF
----------------------------------------------------------------------
[jbjs.pdf]
  -> C:\work\anydoc\jbjs.md
  MinerU 用时 5.4s | 原始 54,194 B -> 输出 12,933 B
  图片占位 1 处 | HTML 标签 18 -> 10（删样式标签） | 列表符号 22 | 变音符 8
    图 1: 内嵌 base64 | 约 30,728 B

----------------------------------------------------------------------
成功 1 个，失败 0 个，共 1 个
```

**这段输出就是本程序的价值**：它不仅告诉你转了，还逐项告诉你对内容做了什么改动、每张图原来多大。任何一步都可以肉眼核对。

## 2. 它做什么 / 不做什么

### 做

- 调 MinerU 解析 PDF（支持 txt / docx / EPUB / CSV 等 MinerU 能吃的格式，本程序只筛 `.pdf`）
- **5 步后处理**，把原始输出改成适合 LLM 读的文本
- 输出到**源 PDF 同目录、同名**的 `.md`，覆盖已存在的
- 逐文件打印改动明细，末尾汇总，失败不中断整批
- 支持递归目录

### 不做

| 不做的事 | 原因 / 替代 |
| --- | --- |
| **保留图片** | 图片换成 `[图片 N]` 占位符并记录原始大小。目标产物是纯文本，base64 是浪费 |
| **导出图片文件** | 同上。要图文完整请用 `docx2md.py`（会生成 `.media\`） |
| **重新排序 / 移动内容** | 只做文本层面的替换与清理，不动阅读顺序 |
| **调用云服务** | 全程本地，数据不出机器 |
| **修改源 PDF** | 源文件只读 |

## 3. 后处理的 5 步

这是本程序与姊妹程序 `pdf2md_anydoc.py` 的核心区别。每步都对应 MinerU 输出的一个实测缺陷。

### 步骤 1 · 图片转占位符

MinerU 把图片以 **base64 内联**在 Markdown 里。一张 30 KB 的图约等于 **7 K token 的二进制噪声**，对 LLM 纯浪费。

```
![](data:image/jpeg;base64,/9j/4AAQSkZJRgABAQAAAQABAAD/2wBDAAIBAQEBAQ...)   ← 30 KB 垃圾
```

替换为：

```
[图片 1]
```

同时把每张图的**原始类型与大小记入运行日志**，任何一张都不会静默丢失：

```
    图 1: 内嵌 base64 | 约 30,728 B
```

覆盖四种形态：`data:` URI、`http(s)://` 外链、本地文件路径、空引用。

> 实测效果：单份 4 页文档 **54,194 B → 12,933 B**，删掉 41,213 个字符（几乎全是 base64）。

### 步骤 2 · HTML 标签清理

MinerU 会泄漏出版商 CMS 的样式标签：

```html
<small><span class="docvortex-page-footnote" data-block-type="page_footnote" style="color:#6b7280">...</span></small>
```

这类 `class` / `style` 对 LLM 是纯噪声。处理分两级：

| 标签 | 处理 | 理由 |
| --- | --- | --- |
| `<small>` `<span>` | **整个删掉**，保留内层文字 | 纯样式包装，文字要留 |
| `<sup>` `<sub>` `<table>` `<td>` 等 | **保留标签名，洗掉全部属性** | 语义内容，上标/表格结构不能丢 |

实测一份中文申报表：150 个标签**全部保留**（MinerU 把表格输出成 HTML `<table>`，td 98 / tr 40），洗掉 33 处 `class`/`style`/`data-*` 属性。

### 步骤 3 · 列表符号规范化

MinerU 用字面 `•` 字符表示列表项：

```
• BAP 5 bone-anchored prosthesis
```

严格的 Markdown 解析器**不认 `•` 是列表**，会当普通段落处理。转成标准语法：

```
- BAP 5 bone-anchored prosthesis
```

支持 `• · ‣ ∙ ⁃ ● ○ ▪ ■` 八种符号，保留原有的缩进层级（嵌套列表不受影响）。

### 步骤 4 · 变音符修复

PDF 若用 Type1 字体且**缺 ToUnicode 表**，提取出的变音符会脱落。这是 PDF 层的问题，两个引擎都会遇到，但 MinerU 的处理方式可修：

| 原始 | 说明 | 修复后 |
| --- | --- | --- |
| `Fr¨olke` | 变音符跑到字母前面 | `Frölke` |
| `Frö¨lke` | 变音符落到后面 | `Frölke` |
| `COVID-19 ¨ pandemic` | 跨行时的孤立残片 | `COVID-19 pandemic` |

四种情形依次处理：合并预组合字符 → 词间孤立符连同两侧空格压成单空格 → 行首/行尾孤立符删除 → 紧贴其他字符的裸删。

> 第二条里的**空格收敛**是关键：只删 `¨` 会留下 `COVID-19  pandemic`（双空格）。

### 步骤 5 · 空白收敛

- 去行尾空格
- 连续 3 个以上空行压成 1 个
- 保证恰好一个结尾换行

**代码块内的内容不动**（用 ``` / ~~~ 围栏识别），避免破坏代码缩进。

### 执行顺序与日志

```
图片占位 → HTML 清理 → 列表规范化 → 变音符修复 → 空白收敛
```

日志会区分 HTML 的两种结果，避免「150 → 150」看起来像没干活：

```
HTML 标签 18 -> 10（删样式标签）        ← small/span 被删
HTML 标签 150 个保留（表格），洗掉 33 处属性   ← 表格结构保留
```

## 4. 命令行接口

```
pdf2md_mineru.py <文件或目录> [选项]
```

### 位置参数

| 参数 | 说明 |
| --- | --- |
| `<文件或目录>` | 一个 `.pdf` 文件，或包含 PDF 的目录（**递归**）。传其他类型文件会报错退出 2 |

### 选项

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `--tier 档位` | `basic` | MinerU 解析档位：`flash` / `basic` / `standard` / `advanced`。见 [8.1](#81-四个-tier-怎么选) |
| `--mineru 路径` | 自动定位 | 指定 `mineru-kit` 可执行文件，或其所在目录 |
| `--timeout N` | `600` | 单文件超时秒数。MinerU 要加载模型，比 anydoc 慢，默认给得大 |
| `--no-postprocess` | 关 | 跳过全部 5 步后处理，输出 MinerU 原始结果。**用于对拍和排查** |
| `--keep-raw` | 关 | 保留 MinerU 的原始输出目录，并打印路径。调试用 |
| `--version` / `--help` | — | — |

### 退出码

| 码 | 含义 |
| --- | --- |
| `0` | 全部成功，或目录内没有 PDF |
| `1` | 有文件失败（其余已处理完） |
| `2` | 用法错误：路径不存在、传入非 PDF 文件、`--mineru` 无效 |

## 5. 设计思路

### 5.1 为什么选 MinerU 而不是 anydoc

对同一份 PDF（4 页英文期刊论文）实测：

| 指标 | MinerU | anydoc |
| --- | --- | --- |
| 段落块数 | **59** | 17 |
| 二级标题数 | **4** | 1 |
| 最长文本行 | 2,921 | 2,911 |
| 标题 `## Abstract` | 识别为标题 | 拍平成 `Abstract Background: ...` |

**段落粒度和标题层级是 RAG 分块质量的决定性指标**。anydoc 把整份摘要、声明、页眉页脚、跨页残句全塞进一个 2911 字符的"段落"，分块器没法切。

MinerU 还自带 OCR，扫描件能处理，anydoc 不能。

### 5.2 后处理每条规则都有实测依据

不做「看起来更整洁」的优化。只修**实测确认的具体缺陷**：

| 步骤 | 依据 |
| --- | --- |
| 图片占位 | 实测 base64 占文档 76% 体积，约 7 K token/张 |
| HTML 清理 | 实测 18 个 `<small><span class=... style=...>` 标签 |
| 列表规范化 | 实测 22 行 `•`，严格解析器不识别为列表 |
| 变音符 | 实测 `Fr¨olke`、`COVID-19 ¨ pandemic` |
| 空白收敛 | 实测行尾空格、3+ 空行 |

每条都在运行日志里报数量，可以核对。

### 5.3 为什么删图而不导出

目标是**纯文本**。图片导出成文件后，LLM 读 `.md` 时依然读不到；把 base64 塞进文本则是纯浪费。

折中是**留占位符 + 记日志**：LLM 知道「这里原本有张图」，人工核对时也能从日志查到原始大小。

如果目标是「图文完整地给人看」，用 `docx2md.py`（生成 `.media\` 目录 + 相对路径引用）。

### 5.4 为什么输出到源同目录

和 `pdf2md_anydoc.py`（输出到独立 `_md` 目录）不同，这里选择就地生成：

- 每个 PDF 对应一个 md，一一对应，不存在命名冲突
- 递归处理多级子目录时，各自的 md 留在各自目录里，结构不乱
- 不需要额外的目录管理

代价：源目录会混入生成物。批量跑完记得清理。

### 5.5 为什么提供 `--no-postprocess`

两个用途：

1. **对拍** —— 想看清 MinerU 到底做了什么，跑一次原始的
2. **排查** —— 怀疑某步清洗有 bug 时，只跑原始输出对比

实测同源对比：

```
--no-postprocess:  54,098 B   （原样，有 base64 和 CMS 标签）
默认：             12,885 B   （清洗后）
```

### 5.6 失败必须可诊断

MinerU 的报错原样透传（末尾 12 行），不加工、不吞掉。单个文件的 Python 异常也会被捕获并打印异常类型，不会让整批崩掉。

## 6. 实现方法

### 6.1 整体流程

```
入口（文件 或 目录）
  │
  ├─ 1. 校验与收集
  │     路径存在？                                    否 -> 退出 2
  │     是文件 -> 校验后缀是 .pdf                      否 -> 退出 2
  │     是目录 -> rglob("*") 递归，筛 .pdf，跳过 ~$    为空 -> 退出 0
  │
  ├─ 2. 定位 MinerU                                   见 6.3
  │
  └─ 3. 逐个处理（失败不中断，异常也不中断）
        ├─ 建临时目录（--keep-raw 则保留）
        ├─ 调 MinerU：mineru-kit parse <pdf> -o <tmp> --tier <档位>
        ├─ 在临时目录里找 <文件名>.md
        ├─ 读入（依次尝试 utf-8-sig / utf-8 / gb18030）
        ├─ 5 步后处理（--no-postprocess 则跳过）
        ├─ 写回 源PDF同目录/同名.md   UTF-8 无 BOM
        └─ finally 清理临时目录（除非 --keep-raw）
  │
  └─ 4. 汇总：成功 N / 失败 M；有失败打印清单并返回 1
```

### 6.2 关键实现点

| 点 | 做法 |
| --- | --- |
| **启动外部进程** | `subprocess.run(cmd, capture_output=True)`，不用 shell，避免中文/空格路径的引号问题 |
| **找产物** | 优先 `<tmp>/<pdf名>.md`；找不到则递归取最新的 `.md`（兜底） |
| **读编码** | `utf-8-sig` → `utf-8` → `gb18030` 依次尝试；全失败则 UTF-8 容错解码。兼容带 BOM 和国内旧编码 |
| **写编码** | `write_bytes(text.encode("utf-8"))`，明确**不带 BOM** |
| **代码块保护** | `_segments()` 用 ` ``` ` / `~~~` 围栏把文本切成「块内/块外」交替片段，HTML 清理和空白收敛只作用于块外 |
| **中文花屏** | `main()` 里 `force_utf8_stdout()` 强制 stdout/stderr 为 UTF-8 |
| **临时目录** | `convert_one()` 创建，`finally` 清理；`--keep-raw` 时跳过清理并把路径写进日志 |
| **异常兜底** | 主循环 `try/except Exception`，单个文件的意外异常记为失败，不影响其余文件 |

### 6.3 MinerU 的定位策略

| 优先级 | 途径 | 说明 |
| --- | --- | --- |
| 1 | `--mineru 路径` | 显式指定。无效时**立即报错退出 2，不静默回退** |
| 2 | 环境变量 `MINERU_KIT_EXE` | 无效时同样报错 |
| 3 | PATH（`shutil.which`） | 命中 `mineru-kit` / `mineru-kit.exe` |
| 4 | `<脚本目录>/mineru/.venv/`、`.venv/`、`venv/` | 覆盖常见的项目虚拟环境布局 |
| 5 | 有限广搜 | 脚本目录、用户目录，深度 ≤ 4，跳过 `node_modules` / `site-packages` / `.cargo` 等 |

全部未命中时，错误信息会**列出所有已尝试路径**并给出三条解决办法（pip 安装 / 设环境变量 / 本次指定）。

> **本机注意**：存在两份 MinerU。PATH 命中的是
> `C:\Users\...\Python313\Scripts\mineru-kit.EXE`（全局安装），
> 而 `F:\work\rtest\mineru\.venv` 下还有一份。**PATH 优先**，想用 venv 那份必须显式指定。

### 6.4 文件筛选规则

```python
p.suffix.lower() == ".pdf"        # 忽略大小写
not p.name.startswith("~$")      # 跳过 Word 锁文件
p.is_file()                      # 只收文件
target.rglob("*")                # 目录输入时递归
```

## 8. 使用注意点

### 8.1 四个 tier 怎么选

MinerU 有 4 档解析精度，影响速度和质量：

| 档位 | 特点 | 适用 |
| --- | --- | --- |
| `flash` | 最快 | 纯文本 PDF、只求快 |
| **`basic`（默认）** | 速度与质量平衡 | **大多数场景** |
| `standard` | 更细致 | 复杂表格、多栏排版 |
| `advanced` | 最慢最准 | 学术论文、图表密集 |

同一份 4 页文档实测 `basic` 约 5~9 秒。档位越高越慢。

### 8.2 慢，比 anydoc 慢一个数量级

| | 单文件耗时 | 原因 |
| --- | --- | --- |
| `pdf2md_mineru.py` | **5 ~ 9 s** | 要加载模型、跑版面分析 + OCR 检测 |
| `pdf2md_anydoc.py` | **~0.1 s** | 纯 Rust 解析，无模型 |

批量处理上百个文件时要预留时间。**只想快速看一眼内容，用 anydoc 版。**

### 8.3 输出会覆盖源目录里的同名 `.md`

`X.pdf` → `X.md`，直接覆盖。**手改过的 md 会在重跑时丢失。**

### 8.4 递归会扫到子目录

和 anydoc 版不同，本程序对目录输入是**递归**的。深层目录下如果有大量 PDF，会全部处理。

输出也各自落在对应源文件旁边，不会全堆到一处。

### 8.5 图片信息只进日志，不进 md

`.md` 里只有 `[图片 1]`。原始大小、类型在**运行时的终端输出**里，不在文件里。

需要事后核对，重跑时加 `--keep-raw`，或先保存运行日志。

### 8.6 HTML 表格保留意味着产物不是纯 Markdown

MinerU 对复杂表格输出 HTML `<table>`，本程序**保留**（只洗属性）。

这在 GitHub / VS Code 里能正常渲染，但对某些只认纯 Markdown 管道的 LLM 工具链可能不友好。

判断方法：看日志里出现

- `HTML 标签 18 -> 10（删样式标签）` → 有 `<sup>` 等零星标签，正常
- `HTML 标签 150 个保留（表格）` → 表格密集型文档，考虑是否需要额外转成 Markdown 管道表

### 8.7 变音符修复是启发式

只在两种明确上下文下生效（`¨` 紧跟元音 / `¨` 两侧是空格）。规则保守，但仍可能：

- 漏掉某些跨行拆散的变音符
- 误删本就是独立 `¨` 的极少数情况

日志会报修复数量，如果数量异常大（比如超过文档里变音符的实际总数），需要人工检查。

### 8.8 输出是 UTF-8 无 BOM

`.md` 文件用标准 UTF-8、不带 BOM。用记事本以外的编辑器打开不会有乱码问题（Windows 记事本从 Win10 1803 起能正确识别 UTF-8）。

## 9. 已知限制

以下是已确认、当前接受不修的。

1. **不保留图片，也不导出图片文件。** 目标产物是纯文本。见 [5.3](#53-为什么删图而不导出)。

2. **不处理私有区字符（PUA）。** 某些 PDF 用符号字体画复选框，会映射到 U+E000–U+F8FF。例如实测一份中文申报表里有 `U+F0A3` ×2、`U+F052` ×1，出现在「导师级别」那行的方框位置，LLM 无法识别。当前不处理。

3. **不修复 `X 5 Y` 形式的分隔符。** PDF 字体映射错误时，破折号或项目符号可能变成数字 `5`，例如 `BAP 5 bone-anchored prosthesis`（本应是破折号）。用正则猜测有误伤正文合法数字的风险，故不处理。

4. **HTML 表格不转成 Markdown 管道表。** 保留 HTML 是为了不丢合并单元格等信息，但产物无法被只认纯 Markdown 的工具解析。

5. **不重排内容、不修复阅读顺序。** MinerU 判定顺序有误时（如多栏排版），本程序原样保留。

6. **每次调用都新建 MinerU 进程。** 批量时模型反复加载，浪费时间。MinerU 本身提供 API 模式（`mineru-api`）可复用常驻进程，本程序未用。

7. **`--tier` 不支持批量差异化。** 整批用同一档位。

## 10. 故障排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `找不到 MinerU（mineru-kit）。已尝试：...` | 没装或不在 PATH | `pip install mineru`；或 `--mineru`；或设 `MINERU_KIT_EXE` |
| 跑的不是预期的 MinerU 版本 | PATH 里有多个副本 | 看启动横幅打印的路径；用 `--mineru` 显式指定 |
| 首次运行很慢 / 提示下载 | 首次需下载模型 | 等待，或用 `mineru-models-download` 预下载 |
| `MinerU 退出码 1 ... Unsupported file type` | 文件不是真 PDF，或扩展名与内容不符 | 确认文件真实格式 |
| `MinerU 未产出 .md 文件` | 输出目录被清空，或模型异常 | 加 `--keep-raw` 保留现场检查 |
| `转换超时（超过 600 秒）` | 文件极大或卡死 | 调大 `--timeout`；单独测 MinerU |
| `.md` 里出现 `[图片 1]` 但找不到原图 | 设计如此 | 看运行日志的「图 N」行；或用 `--no-postprocess` 看原始 |
| 变音符没修好 | 上下文不符合启发式 | 人工处理；日志会报实际修了几个 |
| 表格在某些工具里不渲染 | 产物含 HTML `<table>` | 见 [8.6](#86-html-表格保留意味着产物不是纯-��arkdown) |
| 终端中文花屏 | PowerShell 用 GBK 解码 UTF-8 | 终端执行 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`（只影响显示，不影响文件） |
| `.md` 文件中文乱码 | 用错编码打开 | 产物是 UTF-8 无 BOM，用 UTF-8 打开 |

诊断技巧：先用 `--no-postprocess` 跑一遍看 MinerU 原始输出，判断问题出在引擎还是后处理。

```powershell
python pdf2md_mineru.py 论文.pdf --no-postprocess --keep-raw
```

## 12. 与 pdf2md_anydoc.py 的对比

### 基本差异

| | **pdf2md_mineru.py**（本文档） | pdf2md_anydoc.py |
| --- | --- | --- |
| 引擎 | MinerU 4.0.8 | anydoc 0.2.4 |
| 输入 | 文件 **或目录（递归）** | 仅目录（不递归） |
| 输出位置 | 源 PDF 同目录同名 `.md` | `<目录名>_md\` |
| **后处理** | **5 步**（见第 3 章） | **无** |
| 单文件耗时 | 5 ~ 9 s | ~0.1 s |
| `--tier` 档位 | 支持 | — |
| `--no-postprocess` | 支持 | — |
| `--keep-raw` | 支持 | — |
| OCR | **支持**（MinerU 自带） | 不支持，扫描件失败 |
| 退出码 | `0` / `1` / `2` | `0` / `1` / `2` |

### 同源 PDF 实测（4 页英文期刊论文）

| 检查项 | pdf2md_mineru.py | pdf2md_anydoc.py |
| --- | --- | --- |
| **段落块数** | **59** | 17 |
| **二级标题数** | **4** | 1 |
| 输出体积 | 12.9 KB | 13.0 KB |
| 图片 | 1（`[图片 1]` 占位） | **0**（丢失） |
| CMS 标签残留 | 0（清洗后） | 0（本来就无） |
| Markdown 列表 `- ` | 22 | 22 |
| 变音符 `Frölke` | **正确** | `Fr¨olke` |

### 该选哪个

```
要喂给 LLM / 做 RAG          -> pdf2md_mineru.py   ← 分块质量的关键在段落粒度和标题
有扫描件 / 图片密集文档        -> pdf2md_mineru.py   ← anydoc 不能 OCR
只想快速预览内容              -> pdf2md_anydoc.py   ← 快一个数量级
想看清引擎原始行为 / 对拍      -> pdf2md_anydoc.py
文件数上百、赶时间            -> pdf2md_anydoc.py   ← 5~9s × 100 = 十分钟级别
```

### 还可以怎么组合

- 粗筛阶段用 anydoc 版快速过一遍，确认值得细读的文件，再用 MinerU 版正式转换
- 两份产物对拍，人工检查清洗步骤有没有误伤
- 同一份 PDF 两版都留着，作为质量回归的基线
